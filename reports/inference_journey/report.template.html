将调用变成设备任务

PyTorch / torch-npu / Triton 接口进入主机队列与 CANN 下发路径，提交计算、搬运、event 或设备图重放。

NPU · COMPUTE + MEMORY

读取数值、计算并写回

权重、激活和 KV 主要位于 NPU HBM。设备执行 kernel；生成结果回到 CPU，驱动下一轮调度或响应。

02 / WHERE THE DATA LIVES

tensor 的对象在 CPU，数值可以在 NPU

Tensor 描述一块数值存储及其形状、类型、步长和偏移。Python 拿到的是对象及存储引用；device=npu:0 的 tensor，其数值由设备存储承载。读取 shape 与读取设备上的每个元素，是不同的操作。

03 · NPU / DEVICE MEMORY

参与数值计算的数据

  • 权重 + 各层 KV cache权重跨请求复用；KV pool 跨请求存在，块占用随生命周期变化。

常规推理不需要每轮把完整 KV 搬回 CPU。 CPU 管块 ID，NPU 直接读写 KV 数值。P08 为了验证正确性，主动把第一层触及的 KV 复制回 CPU 比较，这会带来额外同步；P09 / P11 没有做这种诊断性数值读回。

为什么只比较 data_ptr 还不够？

P11 的 decode Q/K/V 共享同一个底层 storage，但 storage offset 分别是 0、896、1024 个 BF16 元素。地址相同或共享 storage，不代表访问相同元素；还要看 offset、shape、stride。地址可能被 allocator 复用，也不能单凭地址认定逻辑生命周期没变。

对连续的第一层 K cache，一个元素的地址为 base_K + (((block×128 + offset)×2 + head)×64 + dim)×2 bytes。V 使用自己的 base。这里是当前布局的地址公式，不把所有模型的布局都假定相同。

03 / MODEL → OPERATOR → KERNEL

模型定义计算，后端选择实现

Qwen2 模型决定 24 层、14 个 Q heads、2 个 KV heads 和 MLP 结构；vLLM-Ascend 各模块根据硬件、配置和可用实现，选择 PyTorch / torch-npu、ATB、自定义 C++ 或 Triton 路径。选择不只发生在 vllm_ascend/attention。

Embedding→RMSNorm→QKV projection→Q/K RoPE→KV 写入 + Attention→O projection→残差 / Norm / MLP↻ 24 层Final norm→LM head / 采样

K、V 是怎样产生的？

Q = XWq　 K = XWk　 V = XWv
Attention ≈ softmax(QKᵀ / √d + mask) V

这是省略 bias、RoPE 与 grouped-query head 对应关系的数学示意。X 是这一层的输入激活。K 用于和 Q 计算相关性，V 是加权汇总的内容；它们都是向量，不是 token 的文字。存入 cache 的是各层本轮新 K/V。

为什么先有 KV，再有新 token？

本轮输入 token → 24 层分别生成 K/V 并完成 attention → final norm / LM head → logits → 采样出下一个 token。

下一轮再为这个新 token 生成它的 KV。prefill 同时处理 prompt 中多个位置，decode 通常只处理上轮生成的一个位置；此处未启用 speculative decoding。

04 / ASYNCHRONOUS EXECUTION

Python 返回时，NPU 可能还没开始

设备地址可以作为算子参数传递，命令先进入队列，再由另一个主机线程下发。CPU 往前执行与 NPU 执行任务，是两条可以重叠推进的时间线。--no-async-scheduling 关闭的是调度策略，不是所有异步设备命令。

一个真实例子：首层 prefill 的 KV 写入

P09 · stream 46 / task 1339 · ReshapeAndCacheNdKernel。以该 Python scope 返回为零点；不是整条线程空闲状态图，也不是未插桩性能基准。原始关联与时间戳

怎样知道真的是同一个任务？

async_task_queue 关联 Enqueue / Dequeue；HostToDevice 关联 CANN launch / device；async_npu 关联框架算子 / device。

还核对 correlation ID、CANN connection ID，以及 CSV 中的 task / stream / 时间。不能靠“两个事件时间挨得近”建立身份对应。

异步不意味着无序

P11 第一层 KV 写入与 FIA 在同一 stream 46，已核对 KV kernel 结束后 FIA 才开始。跨 stream 则需要明确的 event / wait 等依赖，不能套用这个局部结论。

CPU 读取采样结果时需要等待所需数据就绪；Event::synchronize 是等待，copy 是搬运，kernel 是计算，三者职责不同。

另一个 P09 例子中，decode FIA 在 Python 返回前 15.979 µs 已开始，却在返回后 5.062 µs 才结束。因此准确说法是“主机返回与设备完成不是同一个事件”，不能说所有 kernel 都在 Python 返回后才开始。

一个容易漏掉的数据依赖：attention 返回 None，却产生了结果

submod_0 → Q / K / V / output buffer
                           │
           attention(..., output)  ← ForwardContext 中的 KV cache
                  │        │
              return None  └─ 原地写入 output
                                  │
                      submod_2: view(output) → O projection

只看 attention 的 Python 返回值，会误以为它没有输出。实际上它修改传入的 buffer；后续 view 仍指向这块存储，O projection 再读取数值。必须结合 mutates_args / schema 与 alias 关系补足写后读依赖。

view 本身可以只创建张量视图，并不一定读取全部数值；真正消费数值的是后面的计算。FX 中补充的 mutation 边表达依赖，不能自动当作 NPU event 或 fence 的观测。

结论结构化证据

这次总结仍然没有证明什么

  • 尚未构建真实 serving 环境的 KV lifetime violation detector。教学练习的 generation tag 不是 vLLM 已有检测功能的证据。
  • 尚未追踪真实 request 的 free → reuse 与所有在途 kernel 的关系；scheduler 释放、物理清零、设备完成是不同事件。
  • 未覆盖多请求 continuous batching、prefix sharing、多卡通信、量化、MoE 或 speculative decoding；不能把本例路径推广成所有模型的固定实现。
  • 未建立每个 FX 节点到每个重放 kernel 的映射，也未追踪 kernel 内部片上搬运、指令及完整编译 / 二进制部署过程。
目前最可靠的认识： request 看到逻辑序列，allocator 管物理块；模型在 NPU 生成数值，KV pool 保存历史；框架与后端提交任务，CANN 与 NPU 按执行依赖推进。理解正确性时，需要同时跟踪数据身份、存储生命周期、执行完成时刻。
