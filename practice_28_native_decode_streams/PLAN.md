# 实施约束与判断标准

本练习接续 P26 的问题：decode kernel 没用满全部核，是否可以只改变 stream 分配来改善利用与完成时间？

## 实验矩阵

- 真实 Qwen2.5-0.5B、BF16、单 NPU、TP1；同一进程、单 CPU 提交线程。
- eager 与原生 PIECEWISE graph 分别建立参考，不混用参考数值。
- 两条独立的原生请求，各固定 10 个输入 token、生成 64 个 token。冻结实际 decode 16/32/47 的输入、KV 和 metadata。
- `same32`：A32/B32；`mixed16_47`：A16/B47。每次恢复同一前态，不让反复执行改变工作量。
- serial：A、B 都提交到 S0；parallel：A→S0、B→S1。两组使用相同模型实现、capsule、graph 对象、事件终点和结果检查。
- 每后端三个独立进程；每场景每策略 12 次，合计 288 个无 profiler pair。每格预热三次。AB/BA、输入交换及策略先后平衡。
- plain 与 PipeUtilization 分开诊断；每个场景、策略分别采 AB/BA 两条 trace。

## 资格门槛

1. 每个独立实例首先匹配其原生请求参考；两场景、两策略、AB/BA、交换输入全部检查。
2. logits、sampled token、logprobs 和整个 KV 池逐元素精确一致且浮点值有限。不放宽容差掩盖竞争。
3. 两实例可共享只读模型数据；可见可写存储范围不相交，graph pool 分离，参数执行前后哈希一致。源码核查后将原生共享的固定 RoPE 查找表列为只读模型数据，另存地址及前后哈希；不把任意 buffer 都视作只读。
4. 图使用原生 dummy capture、原生固定输入地址和分区方案，不用 FULL graph 或手写图替代。
5. 进程内引用绑定可恢复；提交 A 后注入异常，必须排空已提交工作，再恢复及释放资源。

任何真实隔离或数值资格失败均停止正式测量，保留失败证据。可以修复 harness/API 使用错误后新建目录重试；不能覆盖旧证据，也不能把失败试跑当性能结果。

## 观察与结论边界

- 总完成时间：公共 origin 之后提交两个任务、CPU 等待两终点的 wall time；同时保存各设备 event ready time 及 host 提交时间。
- 真并行：以两个任务实际 compute kernel 区间的交集判定，不用外包络、stream 数或 kernel 数替代。
- 归属：CPU scope → flow/CANN connection → 设备任务 → CSV；图内额外依靠 Python graph 对象、Model ID、debug dump 和 replay 完成边界。
- 同步：输入就绪事件 → 两任务；各任务终点 → 最后 CPU join。图内等待与任务顺序单独记录。不得在 A/B 之间加入 CPU 等待。
- 核数字段、流水线 ratio、时间覆盖率分别报告；它们不等于整卡核占用率。没有性能改善也属于有效结果。
- Python 可见存储检查不能穷尽 native 库内部工作区；观测到正确也不是所有输入、版本及调度的并发安全证明。
- 两 runner 的构建、状态切换开销是实验适配成本；结果不是生产服务 QPS，也不是 vLLM 支持同一 runner 任意并行的承诺。

## 恢复

不改已安装源码、配置、运行服务及环境文件。只增加独立实验目录与进程局部缓存。控制器记录自有 PID/进程组，异常先清理，60 秒后才强制终止自有子进程；不用设备 reset。

记录源码/配置哈希、revision、实际导入路径和设备状态。结束后用未安装实验适配器的新进程重跑原生请求，比对 64 token，并再次检查源码哈希及设备无遗留进程。失败试跑同样完成恢复验证。

本任务不包含 commit/push，不修改其他正在进行的练习。
