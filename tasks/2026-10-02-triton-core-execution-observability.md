# 未来任务：以 Triton RoPE 为例，准确记录 NPU 执行核数

- 记录日期：2026-10-02。
- 状态：待开展；本次仅记录目标与实验思路，不进行工具安装、远端采集或源码修改。
- 研究入口：[Triton JIT 与 Ascend launcher](../references/Triton/README.md)。
- 前置证据：[P19 核使用结果](../practice_19_kernel_core_usage/RESULTS.md)、[P26 decode 利用率](../practice_26_decode_utilization/RESULTS.md)、[P30 RoPE 调用链](../practice_30_cpu_submission_timeline/FORWARD_RESULTS.md)。

## 背景与目标

此前部分 graph replay 内的 RoPE 记录中，核数字段为 `0`，报告按 unknown 处理，不能解释为“未使用 Vector / AI Core”。P30 eager 选中的 RoPE 则记录为 `AI_VECTOR_CORE`、`Block Num=1`、设备耗时 `3.320 µs`；编译产物为 `_triton_rope_aiv`。这些证据说明任务类型和启动配置，但还没有完整回答实际有哪些物理核参与、是否同时活跃，以及 graph 零值从何而来。

**目标：研究并使用当前 CANN 支持的工具，以一个真实 Triton kernel 为案例，建立可复现的核使用记录方法，明确能准确测到什么、哪些仍不可观测。**

需要分别定义和记录：

| 信息 | 要回答的问题 | 不能直接等同于 |
|---|---|---|
| 核类型 | 此任务运行在 AIV / AIC / 混合路径中的哪一种？ | 所有计算单元都在工作 |
| grid、启动块数与混合块字段 | launcher 请求了怎样的并行配置？工具字段如何定义？ | 实际物理核数、同时活跃核数 |
| 实际参与的物理核 | 一次 kernel 执行期间，哪些 core ID 参与过？是否能获得可靠记录？ | 任意时刻都有这么多核活跃 |
| 时间上的核活动 | 每个核何时开始、结束，峰值同时活跃多少核？ | 平均利用率或整卡利用率 |
| 流水线利用率 | Vector、Cube、scalar、搬运等计数器测量什么？分母是什么？ | 直接用百分比反推出核数 |

## 思路：先做薄，再做厚

先选一个 RoPE kernel、一个固定输入、单 NPU、单 stream、已预热 eager 路径，把“提交参数 → 设备任务 → 核记录”的关联讲清楚。少量重复用于确认记录可重复即可，不先铺开模型、形状、并发和工具的完整矩阵。

首轮成功的标准是获得可信的记录口径，即使结果是“当前工具只能报告启动块数，无法提供实际物理 core ID”，也应明确保存依据。不要为了得到一个核数而用估计值填补缺失字段。

## 第一步：核查工具能力与指标定义

候选是用户提出的 **msdebug、msprof，以及当前 CANN / MindStudio 版本支持的其他调试或性能分析工具**。先核实工具的准确名称、是否安装、芯片兼容性、权限和使用方式，不预设它们具有相同能力，也不预设 msdebug 能提供逐核执行时间线。

- 记录远端实际 CANN、驱动、固件、torch-npu、Triton 版本和工具路径；依据匹配版本的官方文档、工具帮助及实测输出选型。
- 核查 msprof 等工具能否提供 task 类型、Block Num、Mix Block Num、逐核标识、逐核时间或硬件计数器；记录每项字段的单位、作用范围、聚合方式与限制。
- 核查 msdebug 或实际对应的调试工具是否支持当前 Triton 编译产物、符号/调试信息和逐核状态；若需要 debug 编译、断点或插桩，明确其会改变执行状态，不将调试时间直接视为正常性能。
- 区分 torch-npu profiler 导出的 CSV、CANN 原始记录和分析器派生字段。检查 graph 捕获/replay 是否存在不同的 metadata 上报或关联机制。
- 工具不支持、未采集、字段缺失、字段为零、解析失败分别记录；不统一转成数值 `0`。

## 第二步：最小 eager 案例

优先直接调用当前安装的 Triton RoPE 实现，使用与 P30 单 token decode 对齐的 dtype、head 形状、位置和布局；记录实际实参，不凭模型名称推定。必要时沿用 P30 harness 获取参数，再建立独立最小调用。

1. 准备固定 Q/K、positions 与 cos/sin 表，保留参考输出与输入副本。RoPE 会写回 Q/K，每次重复前恢复相同输入，恢复操作单列在目标范围之外。
2. 完成 JIT 编译及预热，固定 kernel hash；初始化和编译记录与正式执行分开。
3. 记录 kernel 名称、编译 metadata、grid、launcher 的实际启动参数、device/stream 身份。`function` 和内存指针是句柄或地址，不作为 core ID。
4. 用选定的一种工具采集少量调用，将 Host launch、运行时 task 和设备 kernel 精确关联；记录可获得的核类型、块数、核标识/活动或计数器。
5. 保留原始产物、精确命令、工具选项和提取脚本；独立核验输出，并用少量无 profiler 样本披露观测扰动。

若当前接口只能报告逻辑 block ID，应明确它与物理 core ID 的差别。不能仅靠 kernel 中的 `program_id` 或人工打印，宣称已经测到实际物理核数。

## 第三步：最小 graph 对照，调查零值

eager 的工具链和字段语义确认后，再增加同一 kernel、同一输入的一种 graph capture/replay 对照。不立即重跑完整模型。

- 分别保存 capture 和预热后 replay 的记录，使用实际 graph/task/stream 标识关联，不能只靠同名 kernel 或相近时间。
- 比较同类原始字段：零值是原始记录就存在、未上报导致的默认值，还是导出/解析阶段产生？若无法确定，保留具体未解决环节。
- 不将 eager 核数直接填入 graph 缺失字段；不因图内无独立 Python 调用就认定设备未执行。
- 若独立 graph 无法复现 P15 的零值，再选已有模型中的一个捕获分区做最小复现，避免直接扩展成整套 benchmark。

更多 token 规模、多 stream、其他 Triton kernel 或不同 profiler 配置，仅在上述发现需要时追加。
