# Practice 29：提前排队后，多 stream 能否产生计算重叠？

- 记录日期：2026-09-30（Europe/Berlin）。
- 状态：目标与首轮计划已记录，尚未实施。
- 前置证据：[Practice 28 结果](../practice_28_native_decode_streams/RESULTS.md)及[实现与复现说明](../practice_28_native_decode_streams/README.md)。

## 思路：先做薄，再做厚

**先用最简单的几种情况观察机制、读懂代码，再根据发现推进下一轮。不要一开始就建设完整 benchmark 矩阵、覆盖所有后端和边界情况。**

每轮只回答一个明确的问题，保留最少但足以支撑判断的证据。先得到一条可解释的真实时间线，再决定是否增加形状、重复次数、计数器或其他模式。遇到阻塞，先弄清阻塞本身，不为完成矩阵而不断扩大实现。

“做薄”减少的是实验范围和统计规模，不省略必要的数据依赖、结果校验与异常恢复。小样本可以说明观察到的机制，不能包装成稳定的性能收益。

## 要回答的问题

Practice 28 的正式对照没有显示稳定的双流加速；诊断中，第二份计算下发时第一份已经结束，未观察到 A/B kernel 重叠。这尚不能回答：两份独立工作都已提前提交时，设备能否并行执行？

**本练习目标：让 CPU 在 A/B 开始计算前完成两份任务的提交，再观察双流是否产生真实计算重叠，以及放行后的完成时间是否缩短。**

第一步不是证明多流一定更快，而是确认实验确实建立了“两份独立工作已经排队”的条件。

## 第一轮：一个场景、一个后端、三种情况

优先复用 Practice 28 的原生 vLLM / vLLM-Ascend harness：Qwen2.5-0.5B-Instruct、BF16、单 NPU、单 CPU 模型提交线程、每任务 batch=1。只选 `same32`（两个不同请求各自的 decode 32），先用 eager，减少图捕获与图内部流带来的解释成本。

保留原来的模型计算单元 `forward → logits → sample`、独立 KV 和可写资源、已审计的只读共享数据。每次执行前恢复同一输入和 KV 前态；这些准备不混入放行后的设备执行计时。

| 情况 | 提交方式 | 任务分配 | 回答什么 |
|---|---|---|---|
| 正常双流 | 沿用 Practice 28 的正常提交 | A→S0，B→S1 | 当前环境是否仍出现第二份计算到达较晚 |
| 提前排队、单流 | 两份工作排入后再放行 | A/B→S0 | 去掉提前执行机会后的串行对照 |
| 提前排队、双流 | 两份工作排入后再放行 | A→S0，B→S1 | 工作提前就绪后，设备是否真正重叠 |

核心比较是后两组：使用相同门控协议，只改变任务所属 stream。先固定 AB 提交顺序，少量预热和重复观察即可，不预先要求数百组样本或多进程统计。若需要判断收益是否稳定，再增加 AB/BA、重复轮次等对照。

## 先验证“起跑门”，再接入真实模型

期望的流程是：

```text
CPU：准备输入 → 关闭门控 → 提交 A → 提交 B → 放行 → 等待完成
S0：                       等待放行 → A 的计算 → 完成
S1：                       等待放行 → B 的计算 → 完成
```

图示是目标依赖关系，不是已经验证的实现，也不保证 A/B 同时开始。单流对照将两份计算放入同一流，保持 FIFO 顺序。

先用很小的设备任务验证同步原语；这只是门控机制检查，不作为真实模型的性能结果。核对远端实际 CANN / torch-npu 版本、接口和源码后选择实现，不先指定一个未经验证的 Event/Notify 用法。

必须确认：

- 门关闭时，后面的计算不会提前执行，等待本身不靠占用 AI Core 的忙等 kernel 实现。
- 门关闭时，CPU 能继续提交两份工作；区分 Python 调用返回、运行时实际接收任务和设备开始执行，不能只凭 Python 返回认定已提前排队。
- 放行路径不依赖被门阻塞的任务；检查队列背压或隐式同步是否使第二次提交无法完成。
- 不假设“等待尚未 record 的普通 Event，随后再 record”就一定构成门控。Event 类型的语义不同，需在安装版本上核实。

参考：[CANN Event 记录语义](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/910beta2/API/runtimeapi/aclcppdevg_03_0083.html)。该文档只作为查阅入口，不替代安装版本的源码及实机验证。

如果真实执行路径无法在门关闭时提交完两份任务，先保存具体阻塞位置。本轮的有效发现可以是“卡在何处”，不能将不满足前提的结果解释为硬件无法并行，也不通过删去必要同步来强行跑通。

## 第一轮只保留这些证据

1. **一份简短运行记录**：版本、配置、命令、固定输入状态与本轮实际做了什么。
2. **每种情况的代表时间线**：CPU/CANN 提交、放行、A/B 实际 kernel 区间、完成事件。优先复用 Practice 28 的关联工具，不先重建大报告系统。
3. **正确性**：沿用原生参考，检查 logits、token、logprobs、KV；失败时停止性能解释，不放宽容差掩盖问题。
4. **少量无 profiler 耗时**：分别记录放行后至两任务完成的时间，以及含提交／门控的整个执行时间。前者研究预排队后的执行潜力，后者披露机制开销；不能将前者直接称为端到端加速。

重叠按实际计算区间求交，不按两个 forward 的外包络或 stream 数判断。Profiler 只用于解释时间线，无 profiler 样本才用于耗时比较。第一轮暂不增加 PipeUtilization 等硬件计数器。

## 看完第一轮，再决定如何“做厚”

| 第一轮发现 | 下一步只增加与发现有关的内容 |
|---|---|
| 已提前排队，双流重叠且更快 | 增加 AB/BA 和少量独立重复，确认方向，再考虑 graph |
| 已重叠，但完成时间没有缩短 | 检查单个任务是否变慢；有必要时再加核／流水线计数器研究竞争 |
| 确认两份工作都已提交，仍无重叠 | 检查隐式依赖、运行时调度和放行是否有效，不直接归因于“核已满” |
| 无法在门关闭时提交第二份工作 | 定位 Host 同步或队列背压，先理解阻塞，再选下一种提交方式 |

PIECEWISE graph、`mixed16_47`、输入交换、更多模型／形状、更大样本数及完整报告均为后续选项，不是首轮验收条件。原先讨论的“正常／门控 × 单流／双流 × eager／graph”完整矩阵保留为扩展方向，**不默认一次做完**。
